## 1. Executive Summary

The **Emergency Response Simulator** is a Command and Control (C2) training platform focused on high-level cognitive and organizational skill development for dispatchers, incident commanders, and agency chiefs. It recreates the high-stress, information-heavy environment of an Emergency Operations Centre (EOC) or mobile command post, forcing leaders to manage logistics, communication, and overall crisis strategy.

The simulator is not a video game. Its interface resembles a high-tech data dashboard, centred on a **Common Operating Picture (COP)** that aggregates live simulated GIS data, weather, plume models, and real-time vehicle tracking. Supporting modules include resource and status boards, multi-channel communication hubs, and an **Incident Action Plan (IAP) Builder** based on the FEMA Incident Command System (ICS).

The system injects controlled chaos into a digital control room. The trainee assesses the COP, dispatches resources, and adapts as the simulation dynamically updates. The core training value lies in **managing the fog of war**, optimising limited resources, enabling inter-agency interoperability, and conducting detailed after-action reviews.

From v1.1 onward the simulator is designed as a **client–server system**, enabling multiple trainees, an instructor, and observers to share a single live incident over a LAN. Standalone single-player mode remains supported for individual training and testing.

## 2. Vision and Objectives

### 2.1 Vision

To create the definitive C2 simulator that builds **cognitive and organizational muscle memory** for emergency response leaders, enabling them to make better decisions under pressure, with incomplete information, and across multiple agencies.

### 2.2 Primary Objectives

- **Manage the Fog of War:** Train leaders to make critical, life-or-death decisions using incomplete, delayed, or contradictory information.
- **Resource Optimization:** Teach users to balance limited resources, hold back reserves, and trigger mutual-aid agreements.
- **Interoperability & Joint Command:** Force different branches (Police, Fire, EMS, Coast Guard) to communicate through unified channels, preventing siloed operations.
- **After-Action Review (AAR):** Log every keystroke, radio transmission, and dispatch decision to generate precise data timelines showing where decision-making broke down.
- **Team Training:** Support multi-role exercises with an instructor, observers, and AI role players, so individuals and teams can be trained, assessed, and certified.

### 2.3 Design Principles

- The COP is **not** a “truth screen.” It is the best available representation of what the organisation currently believes is happening.
- The player should sometimes make the correct decision with incomplete information and still have an incident deteriorate. The objective is not perfection; it is good decision-making under uncertainty.
- Reality diverges from the plan. The system must model friction, failure, and changing conditions.
- **The server is the single writer.** The simulation engine is authoritative; clients are untrusted. All state changes flow through the event stream.

## 4. Core Concepts and Terminology

| Term | Definition | Key Question |
|------|------------|--------------|
| **COP** | Common Operating Picture — a continuously updated, shared representation of the current situation. | What is happening? |
| **C2** | Command and Control — the system that enables decisions and actions. | What are we going to do? |
| **IAP** | Incident Action Plan — the formal plan for an operational period. | What should we do? |
| **ICS** | Incident Command System — the organisational framework. | Who is responsible for what? |
| **GIS** | Geographic Information System — geographically referenced data. | What exists where? |
| **AVL** | Automatic Vehicle Location — real-time tracking of mobile resources. | Where are my resources now? |
| **Plume Model** | Prediction of hazard dispersion through the environment. | Where is the hazard going? |
| **Simulation Engine** | The backend that maintains the true state of the world. | What is actually happening? |
| **Session** | A live multiplayer exercise hosted on a server, with participants, roles, and an event store. | Who is taking part? |
| **Participant** | A connected human user with a display name, role, and optional agency affiliation. | Who is this? |
| **Actor** | The identity stamped on every event and command — a participant, the instructor, an AI system, or the environment. | Who did this? |
| **Role Player** | A party (unit, agency, caller, journalist, official) that can be controlled by AI, the instructor, or a human. | Who is playing them? |
| **Truth Group** | The server-side audience that receives ground-truth events (instructor, observers granted truth). | What do they see? |

## 5. System Architecture Overview

The simulator is a modular architecture with a clear separation between the **simulation engine (server)** and one or more **clients**. Standalone single-player mode collapses the two into one process.

### 5.1 High-Level Architecture (Client–Server)

```
                    ┌──────────────────────────────────────┐
                    │        SERVER (ASP.NET Core)         │
                    │                                      │
                    │  Simulation Engine · Event Store     │
                    │  GIS · AVL · Plume · Comms · AI      │
                    │  Session Hub · Voice Router          │
                    │  Command Gate · Authorizer           │
                    └───────────────┬──────────────────────┘
                                    │  SignalR
                 ┌──────────────────┼──────────────────┐
                 │                  │                  │
        ┌────────┴────────┐ ┌───────┴────────┐ ┌───────┴────────┐
        │  Trainee Client │ │ Instructor     │ │ Observer       │
        │  (COP, C2, IAP) │ │ Client (truth) │ │ Client (read-  │
        │                 │ │                │ │  only + notes) │
        └─────────────────┘ └────────────────┘ └────────────────┘
```

### 5.2 Standalone Mode

For individual training, testing, and demonstration, `--Mode=Standalone` runs the engine, event store, services and UI in a single process, with today’s dependency injection. All multiplayer features degrade gracefully: the single user holds every trainee role (ICS doctrine: the IC retains unfilled functions).

### 5.3 Core Modules

1. **Simulation Engine** — Maintains the true world state: weather, fire spread, chemical release, traffic, casualties, hospital capacity, resource movement. Single writer through `SimulationEngine._gate`.
2. **Event Store** — Append-only, time-stamped event stream. PostgreSQL in server mode; in-memory allowed for Standalone and tests. The current COP is a projection of this stream.
3. **Common Operating Picture (COP)** — `PerceivedState.Apply(SimEvent)` builds the perceived world from the event stream. Identical code runs on server and client.
4. **Command & Control (C2)** — Dispatch, orders, reassignments, requests, approvals. 44 methods on `IC2Service`.
5. **IAP Builder** — Structured forms for objectives, organisation, assignments, communications, medical, safety. `IIapService`.
6. **GIS Service** — Static and dynamic geographic data. PostgreSQL + PostGIS.
7. **AVL Service** — Vehicle location, status, speed, heading.
8. **Plume/Hazard Model** — Dispersion predictions, hosted in a Python service.
9. **Communications Hub** — Simulated radio, chat, emergency calls, field reports. `ICommsService`.
10. **Voice Router** — Real audio transport for push-to-talk, with degradation applied per transmission.
11. **After-Action Review (AAR)** — Event timeline, metrics, replay, per-participant filtering. `IAarService`.
12. **Instructor Console** — Scenario control, live injects, role-play, player monitoring.
13. **Session Hub** — Participant registry, roles, permissions, attribution.

### 5.4 Data Flow

The COP is the central nervous system. Almost every subsystem feeds information into it or consumes information from it. Underneath all of it is a **time-stamped event stream**:

```
14:31:04  CALL RECEIVED          "Explosion reported."            Actor: Dispatcher
14:31:18  INCIDENT CREATED       INC-00241, Priority: High        Actor: Dispatcher
14:31:31  UNIT DISPATCHED        Engine 12                        Actor: Operations
14:33:12  UNIT STATUS            Engine 12 → En Route             Actor: System
14:36:42  UNIT STATUS            Engine 12 → On Scene             Actor: System
14:36:59  FIELD REPORT           "Multiple casualties."           Actor: Engine 12
14:37:04  INCIDENT UPDATE        Priority: Critical               Actor: IC
14:37:12  RESOURCE REQUEST       4 additional ambulances          Actor: Logistics
```

Every event carries an `ActorId` and `ActorRole`. The current COP is the current state generated from that event history. This allows reconstruction, replay, delayed information, per-participant attribution and evaluation.

### 5.5 Visibility and Truth Separation

The engine distinguishes **Truth** events (ground truth) from **Perceived** events (what the organisation believes). In server mode, the hub enforces visibility:

- Trainee connections receive only Perceived events.
- The `truth` group (Instructor, and observers granted truth) additionally receives Truth events and 1 Hz `WorldSnapshot` / `LiveTraffic` updates.

This guarantees the fog of war cannot be bypassed by a modified client.

## 6. Common Operating Picture (COP)

*(unchanged from v1.0 — see previous revision for full detail)*

### 6.1 Definition

A COP is the central visual representation of an incident that lets everyone answer: **“What is happening right now, where is it happening, what resources are involved, and what do we know about it?”**

It is a **shared operational information system**, not merely a map screen. It combines geography, incidents, resources, status, intelligence, communications, and time. In server mode it is rendered identically on every connected client, driven by the same streamed event feed.

### 6.2–6.11

*(Content preserved from v1.0. Key points restated for continuity:)*

- The map is the heart: base geography, incident information, operational boundaries (Hot/Warm/Cold zones, evacuation zones, command posts, staging areas, landing zones).
- Resources have status and state: AVAILABLE → DISPATCHED → EN ROUTE → ON SCENE → OPERATING → TRANSPORTING → AVAILABLE (or CANCELLED).
- Incidents are first-class objects, not markers.
- The COP has a time dimension: history, replay, and reconstruction.
- Information is not necessarily true: provenance, confidence, and verification status (Known / Reported / Estimated / Suspected / Confirmed).
- Layers prevent unreadability; toggles live in the top, left, and right pop-out panels.
- Alerts make the COP an attention-management system.
- The COP answers "What is happening?"; C2 answers "What do we do?".
- Seven information domains: Incidents, Resources, Hazards, Geography → Situation Data → Reports, Alerts, History → C2 Interface → Command Decisions.

## 7. GIS, AVL, and Plume Models

*(unchanged from v1.0 — see previous revision for full detail)*

- **GIS data** tells the system what exists where. Static vs dynamic layers.
- **Plume models** estimate where a hazard is going or may go. Inputs include release information, weather, terrain. Output is a set of concentration zones. Plumes are predictions, not facts.
- **AVL** tells the system where its own mobile resources are right now. Position, speed, heading, status, ETA.
- **AVL + GIS** enables routing, ETA calculation, and complication injection (road closures extending ETA).
- All three are modelled as **separate systems** feeding the COP, so the simulation engine can change the world independently of what the player sees.

---

## 8. Incident Action Plan (IAP) and ICS

*(unchanged from v1.0 — see previous revision for full detail)*

- **ICS** is the organisational framework: Incident Commander, Operations, Planning, Logistics, Finance/Admin. Scalable with span of control.
- **IAP** is the plan for an operational period: strategic → operational → tactical objectives, assignments, communications, medical, safety.
- **IAP Builder** is the structured-form software that produces the plan and pulls information from the COP.
- **Operational periods** structure the incident into successive plans.
- **Simulation loop:** Incident → Information → COP → Assessment → IAP → Operations → New Information → COP.
- The player has three conceptual views: COP ("What is happening?"), IAP Builder ("What should we do?"), C2 ("Make it happen.").

---

## 9. Command and Control (C2)

The C2 system is where the player makes things happen. It includes:

- **Dispatch:** Assign units to incidents.
- **Orders:** Issue directives to operations, groups, sectors.
- **Reassignments:** Move resources between incidents.
- **Requests:** Request mutual aid, additional resources, specialist teams.
- **Notifications:** Alert hospitals, utilities, government agencies.
- **Approvals:** Authorise evacuations, requests, spending.
- **Communications:** Radio, chat, data feeds.

The C2 interface is tightly integrated with the COP and IAP Builder, forming the command-and-control cycle. In server mode, C2 commands are routed through a **server-side `CommandGate`** that serialises execution, validates state against the current COP, and authorises the caller before publishing. The 44 methods of `IC2Service` (plus `IIapService`, `ICommsService`, `ISimulationControl`, `IAarService`) are mirrored 1:1 by remote proxies, so view models are unchanged between Standalone and Client modes.

## 10. Simulation Engine and AI

*(unchanged from v1.0 — see previous revision for full detail)*

### 10.1 World State vs Perceived State

The simulation engine maintains the **true state** of the world. The player’s COP only knows what has been reported or detected. This separation enables imperfect information, and in server mode it is enforced on the wire by group filtering.

### 10.2 Event Stream

Everything that happens is recorded as a time-stamped event. The current COP is generated from the event history.

### 10.3 Agent-Based Modeling

Responders, civilians, vehicles, media, politicians, AI agencies.

### 10.4 Hazard Models

Fire spread, flood, plume dispersion, structural collapse, traffic gridlock.

### 10.5 Cascading Effects

One failure triggers others.

### 10.6 Dynamic Scenario Updates

Wind, fire spread, release rate, road closures, vehicle movement, casualty count, hospital capacity.

### 10.7 Role-Player Control Model (v1.1)

Every external party (agency control rooms, Regional Duty Officer, National Directorate approvers, media outlets, officials, civilian callers) has a **controller**:

| Controller | Meaning |
|---|---|
| AI | The default. The system plays the role. |
| Instructor | The instructor speaks or decides as this party. |
| Player | A human trainee (e.g. a Garda liaison) runs the party. |

The `AgencyAiSystem`, `InteragencySystem` and `CommandResponseSystem` skip decisions for roles not under AI control. Pending decisions queue for the current controller. Control can be taken over and handed back at any time; the handover is recorded as an event.

## 13. Communications Realism

*(expanded in v1.1 to include real voice transport)*

### 13.1 Text and Typed Radio

- **Radio discipline and protocols:** Plain language, call signs, closed-loop communication, read-backs, channel congestion.
- **Degraded communications:** Dead zones, cell tower failures, radio battery life, interoperability patches, encrypted vs. unencrypted talkgroups.
- **Delays, missed calls, miscommunication:** Messages may arrive intact or corrupted.
- **Language and cultural barriers:** Limited English proficiency, interpreters, trust issues.

### 13.2 Real Voice (Phase 11)

- **Client audio:** NAudio WASAPI capture and playback, Opus 20 ms frames via Concentus.
- **Push-to-talk:** A hardware key or on-screen button. The existing `PttButton` timing logic becomes the real key-up.
- **Voice router (server-side, behind `IVoiceTransport`):**
  - Channel membership follows the role workspace and the channels a player has chosen to monitor.
  - **Half-duplex:** One talker per channel. A second talker receives "channel busy" or doubling, consistent with `CommsSystem` congestion.
  - **Phase 7 degradation is applied to the audio:** `CommsSystem` decides per transmission (clear / garbled / lost / dead zone), and the router applies dropouts and noise, or drops it entirely.
- **Talking to simulated parties:** Voice transmissions to AI crews and agencies are transcribed (speech-to-text via faster-whisper in the existing Python service, with callsign-biased vocabulary) and enter the existing typed push-to-talk path (`TransmitAsync` with held seconds). Read-backs, radio discipline scoring and lost messages work unchanged. The transcript is the event; audio is attached.
- **Recording:** Each transmission is stored as an Opus clip with `RadioAudioRecorded(MessageId, Channel, ActorId, Duration, Uri)`. The AAR timeline plays clips back. Retention is configurable, and a consent notice is shown at join (per Section 25 psychological safety).
- **Fallback:** Typed push-to-talk remains available at all times and is the default for AI-driven text-only channels.

## 21. Instructor Tools, Multiplayer, and Sessions

*(fully rewritten in v1.1 to incorporate the Phase 11 implementation plan)*

### 21.1 Purpose and Scope

Phase 11 turns the simulator from a single-user dashboard into a **team trainer**. It delivers:

1. A **server/client split** so multiple trainees, an instructor, and observers share one live incident.
2. **Sessions, identity, attribution, and concurrency** so every command and message can be traced to its author, and two players cannot both dispatch the same unit.
3. **Roles, permissions, and workspaces** so each ICS function sees what it needs and can do only what it may.
4. An **instructor console** for live injects, player monitoring and role-play.
5. **AI role players** filling gaps (officials, politicians; optionally human-played agencies).
6. **Observer mode** with live assessment notes.
7. **Voice communications** with real audio, degradation, and recording.

### 21.2 Starting Point and the Underlying Gap

Before Phase 11, the engine, event store, COP and all UI run in one WPF process (`App.xaml.cs`). Everything else depends on splitting that into a server and clients. The existing seams make this tractable:

- The COP is already a pure projection of the event stream: `PerceivedState.Apply(SimEvent)` ignores `Truth` events and skips sequences it has already applied.
- `EventJson` is the single wire/storage format for payloads.
- Service contracts (`IC2Service`, `IIapService`, `ICommsService`, `ISimulationControl`, `IAarService`) are what the UI depends on. Remote proxies can implement them, so view models mostly don't change.
- The engine is already the single writer (`SimulationEngine._gate`), so sequence order equals causal order.
- `WorldSnapshot` is an immutable record captured each step, the natural payload for instructor clients.

### 21.3 Architecture Decisions

| # | Decision | Recommendation |
|---|---|---|
| D1 | Server host and transport | **ASP.NET Core server + SignalR**; WPF clients use `Microsoft.AspNetCore.SignalR.Client`. |
| D2 | Keep single-player in-process mode? | **Yes.** `--Mode=Standalone` (today's DI) vs `--Mode=Client --Server=…`. |
| D3 | Identity | **Session join code + display name + role**; instructor PIN. No accounts or passwords (classroom LAN). |
| D4 | Event store for multiplayer | **PostgreSQL required in server mode** (crash recovery, AAR after session); in-memory allowed for Standalone and tests. |
| D5 | Who covers unfilled roles | **The IC holds every unfilled function** (ICS doctrine: the IC retains what isn't delegated). |
| D6 | Voice | **Real audio over the server**: NAudio capture/playback, Opus via Concentus, SignalR streaming behind an `IVoiceTransport`. Typed push-to-talk stays as fallback. |
| D7 | Speech for AI-run parties | **Speech-to-text into the existing push-to-talk path** (faster-whisper hosted in the existing Python service); AI replies stay text (TTS optional later). |
| D8 | Politicians in Phase 11 | **A basic official/politician role player now**; press conferences, social media and legal go to Phase 13. |

### 21.4 Milestones

#### M1 — Server/Client Split (L) · foundation for everything else

**New projects**
- `Emergency Response Simulator.Server`: ASP.NET Core (net10.0). Hosts `AddSimulation`, the event store, `SimulationHostedService`, and a `SessionHub`.
- `Emergency Response Simulator.Client`: SignalR client, remote service proxies, event feed (referenced by the WPF app).

**Event feed**
- On connect, the client sends its last applied sequence. The server replays from `IEventStore.ReadAsync(session, after)` and then streams live events from `Appended`. The client calls `PerceivedState.Apply` for each, so reconnects resume with no gaps.
- **Visibility is enforced on the server:** `Truth` events go only to the `truth` group. Trainee connections never receive them.
- Batch fan-out (e.g. every 100–250 ms) if AVL volume is high. Measure events/s on the Barrow Street scenario first.

**Commands**
- Proxies implement `IC2Service` (44 methods), `IIapService`, `ICommsService`, `ISimulationControl`, `IAarService` over a strongly typed hub, mirroring interfaces 1:1.
- `CommandResult` returns to the caller. Effects arrive through the event feed like everything else.

**Instructor data**
- The server pushes `WorldSnapshot` and the `LiveTraffic` snapshot to the `truth` group at 1 Hz. `InstructorViewModel` reads from a client-side snapshot source instead of `SimulationEngine`.

**Client-side routing**
- The UI uses `IRoutingService` for unit ranking, nearest road, and the congestion layer. Clients load the road network from the same GIS source. If slow, add a server routing endpoint.

**WPF composition**
- `App.xaml.cs` chooses Standalone or Client DI. In Client mode, no engine or systems are registered locally.

**Exit criteria:** Two clients see an identical COP. A trainee connection receives zero Truth events (asserted in a test). Killing and reconnecting a client restores its COP with no gaps. All existing tests pass in Standalone mode.

#### M2 — Sessions, Identity, Attribution, Concurrency (M)

**Session lifecycle:** create (pick a scenario) → lobby → join (code, name, role) → instructor starts → end. New events: `ParticipantJoined(UserId, Name, Role, AgencyId?)`, `ParticipantLeft`, `RoleAssigned`, `RoleHandedOver`.

**Attribution**
- Add `Guid? ActorId` (and `UserRole? ActorRole`) to `SimEvent`/`SimEventDraft`, plus `EventRecord` columns and a migration.
- **The server stamps the actor from the connection identity, never from client input.**
- An ambient `ICommandContext` (AsyncLocal) carries it into `IEventPublisher.PublishAsync`, so the 44 C2 signatures don't change.

**Concurrency**
- C2 checks state then publishes (e.g. `DispatchAsync` checks `unit.Status` then publishes outside the engine gate). Two players can both pass the check.
- Fix: a server-side **`CommandGate`** that runs each command one at a time, with the COP up to date before validation.
- Verify that `PerceivedState` has applied an appended event before the gate is released.

**AAR**
- `AarAnalyzer` metrics per participant (actions, time-to-act, missed alerts by role) and a timeline filter by participant.

**Exit criteria:** Every command event carries its actor. Two simultaneous dispatches of the same unit: exactly one succeeds (test). The AAR timeline can filter by participant.

#### M3 — Roles, Permissions, Workspaces (M)

**Permission matrix.** One attribute per `IC2Service`/`IIapService`/`ICommsService` method, checked by a server-side `CommandAuthorizer`. The UI mirrors it through `CanExecute`, for usability only; the server enforces it.

| Role | May do |
|---|---|
| IC | Everything trainees can do: objectives, zones, unified command, approve IAP, assign ICS posts |
| Operations | Dispatch, reassign, cancel; unit status; groups and divisions; tactics; PAR; relief and rotation |
| Planning | IAP drafts and periods; assess and link reports; situation reports; resource status tracking |
| Logistics | Resource requests, mutual aid, supply and rehab requests |
| Finance/Admin | Cost and time records (read-mostly until Phase 14) |
| Safety | Safety messages, hazard zones, evacuation signal / emergency traffic, stop an unsafe tactic |
| Liaison | Agency chat, unified command invitations, notifications, information requests to agencies |
| PIO | Public statements, media enquiries, joint information centre |
| Dispatcher | Create incidents, initial dispatch, 999 line |
| Instructor | Everything, plus instructor-only commands (M4) |
| Observer | Nothing (read-only) |

**Rules around the matrix**
- Unfilled roles fall to the IC. In Standalone mode the single user holds every role.
- `AssignIcsPositionAsync` gains an optional `userId`, so the ICS chart shows which player fills which post.
- Role handover reuses the Phase 8 handover idea: handover notes are recorded; skipping them loses information.

**Workspaces.** A default layout per role over the **same COP**: which tabs open first, and which comms channels are monitored (Ops: tactical; Liaison: interagency chat; PIO: media).

**Exit criteria:** A permission-matrix test runs for every command × role. An Ops player cannot issue a public statement (refused server-side even if the UI is bypassed).

#### M4 — Instructor Console (L)

**Separate instructor client** (role `Instructor`, `truth` group)
- `InstructorViewModel` and the ground-truth map layers move there. The trainee build hides them, and the server doesn't send them truth anyway.
- Pause, time scale and step become instructor-only in multiplayer.

**Live injects**
- `ScriptedInjectSystem` exposes its injects with status (pending / fired / held / skipped / expired).
- New instructor commands, applied at the next tick:
  - Fire now
  - Hold / release
  - Skip
  - Add an ad-hoc inject from a template library built on existing events: new incident (`WorldIncidentStarted`), wind shift (`WeatherChanged`), mast failure (`CellTowerFailed`), unit breakdown, hospital diversion, secondary device, responder down.
- Each is recorded as `InjectFired/Held/Skipped(id, by)` with source `Instructor`, so the AAR shows instructor intervention.

**Monitor players**
- Live per-participant activity feed (from M2 attribution).
- Idle-time indicators, unacknowledged alerts by role, comms load per player.
- Bookmarks the AAR can jump to.

**Role-play**
- Send on any channel *as* a unit, agency, caller, journalist or official. Trainees see the impersonated source; the AAR marks it as instructor role-play (`ReportSource.Instructor` / `EventSources.Instructor` finally used).
- **Take over / hand back an AI role:** the role-player registry (Section 10.7) governs control. `AgencyAiSystem`, `InteragencySystem` and `CommandResponseSystem` skip decisions for roles not under AI control. Pending decisions queue in the console for the instructor to answer.

**Exit criteria:** The instructor can run the Barrow Street scenario live: fire an inject early, hold another, inject a wind shift, approve a mutual-aid request as the Regional Duty Officer, and phone the IC as a journalist. All of it appears correctly in the AAR.

#### M5 — AI Role Players: Fill the Gaps (S–M)

**Officials/politicians (basic):**
- A `PoliticalPressureSystem` role player (e.g. local TD, council chief executive, minister's office).
- Calls the IC or PIO for updates at intervals that scale with severity, casualties and unanswered media.
- Escalates (alert, then a demand that conflicts with priorities) when ignored.
- Instructor-controllable via the M4 registry.
- Depth (press conferences, social media, legal exposure) stays in Phase 13.

**Human-played agencies (stretch):**
- Replace the binary `Agency.AiControlled` with the registry controller, so a player can run an agency's units.
- Their units take orders only from them, as with AI agencies today.

#### M6 — Observer Mode (M)

- **Read-only client:** the server refuses every command (matrix). Generalise `CopView.IsReplay`'s read-only plumbing to an `IsReadOnly` flag so command controls hide.
- **Views:** perceived only, or perceived plus truth (instructor grants truth per observer). "Follow participant X" shows that player's actions and channels.
- **Live assessment:**
  - Time-stamped observer notes and ratings tagged to a participant and an event sequence: `AssessmentNoteRecorded(ObserverId, ParticipantId, Sequence, Competency, Rating, Text)`.
  - Hidden from trainees: add an `Assessment` visibility, or route through `Truth`.
  - Rubric uses the AAR's competency bands (Competent / Developing / Not yet competent).
- **AAR:** notes appear on the timeline and in `AarExport`; per-participant scoring combines metrics (M2) with observer ratings.

#### M7 — Voice Communications (L)

- **Client audio:** NAudio WASAPI capture and playback, Opus 20 ms frames (Concentus). A push-to-talk key or button (existing `PttButton` timing becomes the real key-up).
- **Server voice router**, behind `IVoiceTransport`:
  - Channel membership follows role workspace and monitored channels.
  - **Half-duplex:** one talker per channel; a second talker gets "channel busy" or doubling, consistent with `CommsSystem` congestion.
  - **Phase 7 degradation applied to the audio:** `CommsSystem` decides per transmission (clear / garbled / lost / dead zone) and the router applies dropouts and noise, or drops it.
- **Talking to simulated parties:** voice transmissions to AI crews and agencies are transcribed (D7) and enter the existing push-to-talk path (`TransmitAsync` with held seconds), so read-backs, radio discipline scoring and lost messages work unchanged. The transcript is the event; the audio is attached.
- **Recording:** each transmission stored as an Opus clip, with `RadioAudioRecorded(MessageId, Channel, ActorId, Duration, Uri)`. The AAR timeline plays clips back. Retention setting; consent notice at join (Phase 21).
- **Exit criteria:** Two players talk on a tactical channel with half-duplex behaviour. A player's spoken order to an AI unit is read back. Every transmission plays back in the AAR.

### 21.5 Cross-Cutting Work

**Tests** (xUnit; in-process server via `Microsoft.AspNetCore.Mvc.Testing` / `TestServer` with several `HubConnection`s)
- Truth never reaches a trainee.
- Reconnect catch-up.
- Concurrent conflicting commands.
- Permission matrix (every command × role).
- Actor stamping can't be spoofed.
- Inject control.
- AI role takeover and hand-back.
- Observer is read-only.
- Voice routing with a fake transport.
- Existing suite runs in Standalone mode.

**Migrations:** `ActorId` and `ActorRole` on events; participants; assessment notes; audio clip metadata.

**Determinism**
- Human and instructor actions are events, so replay and the AAR stay consistent.
- `BranchRunner` re-runs remain single-player and AI-only by design. Document that branches replace human role players with `ExpertPolicy`.

**Performance:** measure event fan-out per client and snapshot size at 1 Hz with 900 civilians; trim or delta-encode if needed.

**Security (LAN scope)**
- The server validates and authorises everything; clients are untrusted.
- Join codes expire.
- No secrets in client configuration.

**Docs:** README sections for running a server, joining, and the instructor and observer guides.

### 21.6 Order and Checkpoints

```
M1 Server/client split ─► M2 Identity & attribution ─► M3 Roles & permissions ─┬─► M4 Instructor console ─► M5 Role players
                                                                                ├─► M6 Observer mode
                                                                                └─► M7 Voice
```

1. **After M1:** demo two WPF clients on one server sharing a COP. *Go/no-go on SignalR (D1).*
2. **After M3:** a full ICS team of 3–4 players runs Barrow Street with the IC covering unfilled roles.
3. **After M4 + M6:** an instructor-led exercise with an observer; AAR shows per-player actions and observer notes.
4. **After M7:** voice exercise; recordings in the AAR.

**Early spike (1–2 days, during M1):** a Concentus + NAudio + SignalR streaming prototype, to confirm latency on the training LAN before committing to D6.

### 21.7 Risks

| Risk | Mitigation |
|---|---|
| UI view models assume in-process services (e.g. synchronous `CommandResult` followed by immediate COP read) | Proxies await until the COP has applied the resulting sequence before returning |
| Truth leaks via snapshots or descriptions | Server-side group filtering plus a leakage test on every event type |
| Speech recognition accuracy on radio jargon and callsigns | Prompt/vocabulary biasing with callsigns from the roster; typed push-to-talk fallback; instructor can correct the transcript |
| Scope creep into Phase 13 (media and politics) | M5 limited to a basic official role player; depth deferred |
| Voice latency over SignalR | Early spike; `IVoiceTransport` lets WebRTC replace it later |

## 26. Technical Architecture and Recommended Stack

*(expanded in v1.1 for client–server specifics)*

| Component | Recommended Language / Tech | Rationale |
|---|---|---|
| User Interface (COP, IAP Builder) | C# (WPF) | Best for data-dense, interactive dashboards. |
| Simulation Engine (Logic, AI, Event Stream) | C# (.NET 10) | Performance, concurrency, dev speed. |
| Server host | ASP.NET Core + SignalR | Mature, strongly typed hubs, easy WPF client. |
| Client transport | `Microsoft.AspNetCore.SignalR.Client` | Same contracts as server; reconnection support. |
| Hazard/Dispersion Modeling | Python | Unmatched scientific libraries. |
| Speech-to-text | faster-whisper (Python service) | Callsign-biased vocabulary; local, no external API. |
| Voice codec | Opus via Concentus | Low bandwidth, low latency, C# friendly. |
| Client audio | NAudio (WASAPI) | Reliable capture/playback on Windows. |
| GIS Data Backend | PostgreSQL + PostGIS | Industry standard for spatial relationships. |
| Event store (server mode) | PostgreSQL | Crash recovery, AAR after session. |
| Event store (Standalone/tests) | In-memory | Speed, isolation. |
| Web-based COP (if needed later) | TypeScript + OpenLayers/Mapbox | Dominant for WebGIS. |

**Why not C++ or Ada?** C++ is overkill for UI-heavy development. Ada/SPARK is for safety-critical systems, not training tools.

## 27. Development Roadmap and Priorities

### 27.1 High-Impact Priorities

1. **Human factors and crew management** — makes resources feel real.
2. **Communications realism** — the core of fog of war.
3. **Multi-agency and public/media pressures** — adds political and social complexity.
